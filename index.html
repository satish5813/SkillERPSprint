How the sprint runs

The clock is the hardest constraint in the room. Everything below exists so that no team loses twenty minutes deciding what to build.

Three roles, five phases, four hard milestones. The first deploy happens at minute 40 with almost nothing working — that is the checkpoint that decides whether a team finishes.

Rules

  • Each team draws one problem ID. Judges may assign a second one to teams that finish early.
  • The five tasks are the deliverable. Extra features score nothing until all five pass.
  • Gmail sign-in must actually work. A hardcoded user fails the round.
  • Data must persist in the assigned database. In-memory arrays fail the round.
  • Push to a public GitHub repo. First commit before minute 35, last commit before minute 120.
  • Seed data script required, so a judge can run the app in one command.
  • It must be live: frontend on Vercel, API and both databases on Railway. Localhost demos are not judged.

What "industry level" means here

  • Server validates every input. The browser is not a security boundary.
  • Money, marks and seat counts move inside a transaction or not at all.
  • Every list endpoint is paginated. Every mutation is idempotent or explains why it isn't.
  • Errors return a code and a message the UI can show, never a stack trace.
  • Loading, empty and error states exist on every screen that fetches.
  • Role checks live in middleware, not in JSX.

Team roles for two hours

  • Schema owner — writes the migration and the seed file in the first 15 minutes, then owns queries.
  • API owner — controllers, validation, auth middleware, Postman collection.
  • UI owner — routes, forms, tables, the three states.
  • Integrator — in a pair, this is whoever is less blocked. Runs the tests at minute 90 regardless.

Scoring at a glance

  • Five tasks complete — 40
  • Five test cases pass, demonstrated live — 20
  • Data model quality: keys, constraints, indexes — 15
  • Auth and access control correctness — 10
  • UI usability and states — 10
  • Bottleneck write-up with evidence — 5

Gmail sign-in: the one spec everybody implements

Firebase Auth issues the token in the browser. The Node API verifies it with the Admin SDK and attaches the user to the request. Nothing else is trusted.

Eight steps. Steps 4 to 7 are the ten auth points. A team that checks the domain only in React has drawn its boundary in the wrong place.

// client: src/auth.js
const provider = new GoogleAuthProvider();
provider.setCustomParameters({ hd: "college.edu" });   // hint, not a guarantee
const { user } = await signInWithPopup(auth, provider);
const idToken = await user.getIdToken();               // send as Bearer on every call

// server: middleware/auth.js
const decoded = await admin.auth().verifyIdToken(token);
if (!decoded.email_verified) throw new AppError(401, "EMAIL_UNVERIFIED");
if (!decoded.email.endsWith("@college.edu")) throw new AppError(403, "DOMAIN_BLOCKED");
req.user = await Users.findOrCreateByEmail(decoded.email, decoded.uid);
if (!req.user.active) throw new AppError(403, "ACCOUNT_DISABLED");

// server: middleware/rbac.js
const allow = (...roles) => (req, _res, next) =>
  roles.includes(req.user.role) ? next() : next(new AppError(403, "FORBIDDEN"));

The domain check belongs on the server. The hd parameter is a UI hint that any client can drop. Teams that only check the domain in React lose the full ten auth points.

Database conventions every problem inherits

Relational (MySQL / PostgreSQL)

  • Surrogate id plus a human code column with a UNIQUE constraint (PO-2026-00042).
  • created_at, updated_at, created_by on every table.
  • Foreign keys declared with explicit ON DELETE RESTRICT; cascade only for true child rows.
  • CHECK constraints for ranges — marks 0–100, quantity > 0, end_date >= start_date.
  • Status columns are ENUM or a lookup table, never free text.
  • Money as DECIMAL(12,2). Never float.
  • Index every foreign key and every column you filter or sort on.

MongoDB, used alongside

  • audit_events — who, what, before, after, at, ip. Append-only, every problem writes here.
  • form_drafts — partially filled forms keyed by user and form type.
  • documents — uploaded file metadata, verification status, reviewer notes.
  • notifications — outbound email/SMS queue with delivery attempts.
  • TTL index on drafts and OTP collections. Compound index on { entityType, entityId, at:-1 }.

Using AI assistants well

Copilot, Claude Code and Codex are allowed on every problem and judges will ask what you delegated. The teams that win are not the ones that prompt the most — they are the ones that review the output fastest.

The four review checks at step 3: is the authorization there, is the transaction there, is every input validated, and does the code reference a table the migration actually creates.

Delegate these

  • Migrations and seed files from a schema you already sketched.
  • Controller and service boilerplate once the contract is written.
  • Table and form components against a field list.
  • Supertest suites from the five test cases, verbatim.
  • Reading an unfamiliar error and proposing three causes.

Do these yourself

  • The data model and the normalization decisions.
  • Transaction boundaries and isolation levels.
  • Anything touching auth, roles or money.
  • Accepting a generated migration without reading the FK actions.
  • Anything the assistant wrote that you cannot explain to a judge.

Prompt shapes that work under time pressure

  • Schema first: "Here is my ER sketch as text. Generate a PostgreSQL migration with FKs, CHECK constraints and indexes. List every assumption you made as a comment."
  • Contract first: "Given this OpenAPI fragment, write the Express controller and a Zod schema. Validation errors must return the shared error envelope."
  • Tests from the brief: "Turn these five test cases into Supertest tests. Include the negative paths. Do not change the expected status codes."
  • Debugging: "This request hangs with no response and no error. Here is the route, the middleware chain and the log. Give me three candidate causes ranked by likelihood."
  • Review: "Review this endpoint for missing authorization, missing transaction and unvalidated input. Only list problems, no rewrites."

Failure modes judges will look for

  • Generated code that queries a table the migration never created.
  • An allow("admin") middleware imported but never mounted.
  • A transaction opened and never committed on the error path.
  • Frontend validation with no server counterpart.
  • Secrets and service-account JSON committed to the repo.
  • Tests that assert 200 on every path, including the ones that should be 403.

PO-01

Vendor master with duplicate-supplier detection

React + Vite + Ant Design · MySQL · MongoDB for the change log

The stores department has three rows for the same supplier because one clerk typed "Sri Sai Traders", another "SRI SAI TRADERS PVT LTD", and a third registered the same GSTIN with a different PAN. Build the vendor master that refuses to let this happen a fourth time.

Tasks
  1. Vendor CRUD with GSTIN, PAN, bank account, category and MSME flag; GSTIN and PAN carry UNIQUE constraints and format CHECKs.
  2. On create, run a fuzzy name match (normalised, punctuation stripped) and show suspected duplicates before the save button activates.
  3. Vendor approval workflow: DRAFT → PENDING → APPROVED → BLACKLISTED, with only the purchase officer able to approve.
  4. Write every field-level change to a MongoDB vendor_audit document with before/after values.
  5. Searchable, server-paginated vendor list with filters on category, status and MSME.
Test cases
  1. Creating a second vendor with an existing GSTIN returns 409 DUPLICATE_GSTIN, not a 500.
  2. "Sri Sai Traders" and "sri sai traders pvt. ltd." both surface in the duplicate warning list.
  3. An invalid GSTIN (14 characters) is rejected by the server even when the client check is bypassed via Postman.
  4. A clerk role calling the approve endpoint gets 403 and no status change is written.
  5. Editing a bank account produces exactly one audit document containing the old and new account numbers.
Bottlenecks
  1. Fuzzy matching with LIKE '%term%' across 25,000 vendors does a full table scan on every keystroke.
  2. Debounce missing on the duplicate-check call, firing one request per character.
  3. Case and whitespace variants defeat the UNIQUE index unless a normalised column is stored and indexed.
  4. Audit writes to Mongo inside the request path add latency; they belong after the response or on a queue.
  5. The list endpoint returns every vendor and paginates in React.

Screens to build: Vendor workbench with search and status filter · Vendor form with a live duplicate-warning panel · Vendor detail with change history · Approval queue for the purchase officer

Data store: vendors(id, code UQ, name, name_normalized IDX, gstin UQ, pan UQ, category, msme BOOL, status ENUM, created_by) · vendor_bank_accounts(vendor_id FK, ifsc, account_no, is_primary) · Mongo vendor_audit{vendorId, field, before, after, by, at}

Minute-90 cut: keep exact-match duplicate blocking and drop fuzzy matching. Never drop the audit log.

PO-02

Purchase order creation with line items and tax

React + Vite + MUI · PostgreSQL · MongoDB for PDF metadata

A department raises a PO with eight line items, each with its own GST rate, some intra-state and some inter-state. Totals must match to the paisa on the printed order and in the ledger.

Tasks
  1. Header plus line-item form: item, HSN, quantity, unit, rate, discount, GST rate, delivery date.
  2. Server-side computation of line total, CGST/SGST or IGST based on vendor state, and grand total in DECIMAL(12,2).
  3. Sequential PO number generation per financial year with no gaps and no duplicates under concurrent creation.
  4. Save as draft and resume, with drafts held in MongoDB until submitted.
  5. Printable PO view with terms, authorised signatory and a rounded amount in words.
Test cases
  1. A line of 7 units at 1,333.33 with 18% GST produces 11,011.97 and the header total equals the sum of lines.
  2. Vendor in the same state yields CGST+SGST; a different state yields IGST only.
  3. Two simultaneous submissions produce PO-2026-00101 and PO-2026-00102, never the same number twice.
  4. Quantity of zero or a negative rate is rejected with a field-level error.
  5. Deleting a line recomputes the total on the server, not just in React state.
Bottlenecks
  1. Computing totals as floats introduces 0.01 drift that reconciliation will find months later.
  2. MAX(po_number)+1 under concurrency issues duplicates; a sequence or a locked counter row is required.
  3. N+1 queries fetching each line item's tax master row.
  4. Re-rendering the whole line table on every keystroke in a 40-line PO.
  5. Draft autosave firing on every change instead of on a timer.

Screens to build: PO builder with an editable line-item table and live totals · Draft list with resume · Printable PO preview · Vendor and item pickers

Data store: purchase_orders(id, po_number UQ, vendor_id FK, department_id FK, status, subtotal, tax_total, grand_total, fy) · po_line_items(po_id FK ON DELETE CASCADE, item_name, hsn, qty CHECK>0, rate, gst_rate, line_total) · po_number_seq(fy, last_value) · Mongo po_drafts with TTL

Minute-90 cut: single tax rate for all lines; keep the sequence safety.

PO-03

Multi-level approval routing by value threshold

React + Vite + Ant Design · MySQL · MongoDB for the approval trail

Below ₹50,000 the HOD signs off. Up to ₹5 lakh it needs the Registrar as well. Above that, the Purchase Committee. The rules change every budget year, so they cannot be hardcoded.

Tasks
  1. Approval-rule table driven by amount band, department and category; an admin screen to edit bands.
  2. On submit, generate the approval chain as ordered steps and route to the first approver.
  3. Approver inbox with approve, reject with mandatory reason, and return-for-correction.
  4. Delegation: an approver on leave nominates a substitute for a date range.
  5. Timeline component showing each step, actor, timestamp and remark.
Test cases
  1. A ₹49,999 PO generates one step; ₹50,001 generates two.
  2. An approver at step 2 cannot act while step 1 is pending — 409 OUT_OF_SEQUENCE.
  3. Rejection at any step moves the PO to REJECTED and no later approver sees it in their inbox.
  4. Editing the amount after partial approval resets the chain and records why.
  5. A delegate acting inside the date window succeeds; one day outside it gets 403.
Bottlenecks
  1. Rules expressed as if/else in the controller — every policy change becomes a deployment.
  2. Approver inbox query joining five tables with no index on (approver_id, status).
  3. Double-click on Approve creates two approval rows without a unique constraint on (po_id, step_no).
  4. Notification emails sent synchronously, so approval takes four seconds.
  5. Amount changed mid-approval with no re-evaluation is an audit failure waiting to happen.

Screens to build: Submit screen showing the generated approval chain · Approver inbox · PO detail with the step timeline · Approval-rule admin table · Delegation setup

Data store: approval_rules(min_amt, max_amt, dept_id, level_no, role) · po_approvals(po_id FK, step_no, approver_id, status, remark, acted_at, UNIQUE(po_id, step_no)) · delegations(from_user, to_user, from_date, to_date) · Mongo approval_events

Minute-90 cut: drop delegation, keep rule-table routing and the sequence guard.

PO-04

Goods receipt note with partial and over-delivery

React + Vite + Tailwind · PostgreSQL · MongoDB for inspection photos

The vendor ships 60 of 100 chairs today and 45 more next week. Five arrive damaged. The GRN must track received, accepted and rejected quantities per line without ever letting the total exceed the PO plus the tolerance.

Tasks
  1. GRN against a PO showing ordered, already received and pending quantity per line.
  2. Capture received, accepted and rejected quantities with a rejection reason.
  3. Enforce cumulative receipt ≤ ordered × (1 + tolerance%) inside a transaction.
  4. Auto-transition the PO to PARTIALLY_RECEIVED or CLOSED based on all lines.
  5. Upload inspection photos; store file metadata and reviewer notes in MongoDB.
Test cases
  1. Receiving 60 then 45 against an order of 100 with 2% tolerance rejects the second GRN.
  2. accepted + rejected must equal received; a mismatch returns 422.
  3. After the final line is fully received, PO status flips to CLOSED automatically.
  4. Two storekeepers posting GRNs simultaneously cannot both pass the tolerance check.
  5. A GRN against a cancelled PO is refused.
Bottlenecks
  1. Reading pending quantity, then writing, without SELECT … FOR UPDATE — a classic lost update.
  2. Recomputing received-to-date by summing all historical GRNs on every page load.
  3. Storing image binaries in the database instead of object storage with metadata.
  4. PO status derived in the UI, so two screens disagree.
  5. No index on grn_lines(po_line_id), making the running total slow as receipts accumulate.

Screens to build: GRN entry showing ordered, received and pending per line · Receipt history for a PO · Inspection photo upload · Pending-receipt workbench

Data store: grn(id, grn_no UQ, po_id FK, received_on, storekeeper_id) · grn_lines(grn_id FK, po_line_id FK, qty_received, qty_accepted, qty_rejected, reason, CHECK(accepted+rejected=received)) · Mongo grn_attachments

Minute-90 cut: single-shot full receipt is not acceptable; instead drop photo upload and keep partial receipts.

PO-05

Three-way match: order, receipt, invoice

React + Vite + MUI · MySQL (views + stored procedure) · MongoDB for exception notes

Accounts will not pay an invoice unless the PO, the GRN and the bill agree on quantity and rate within tolerance. Today a clerk does this on paper. Automate the match and show only the exceptions.

Tasks
  1. Invoice entry linked to a PO, with invoice number unique per vendor.
  2. SQL view v_three_way_match joining PO lines, accepted GRN quantity and invoice lines.
  3. Stored procedure that classifies each line as MATCHED, QTY_VARIANCE, RATE_VARIANCE or NO_GRN.
  4. Exception dashboard listing only unmatched lines with the variance amount.
  5. Approve-with-reason override for variances inside tolerance, logged to MongoDB.
Test cases
  1. Invoice of 100 units against 95 accepted flags QTY_VARIANCE with a value of 5 × rate.
  2. Invoice rate above PO rate by 1% passes at 2% tolerance and fails at 0.5%.
  3. An invoice with no GRN at all is blocked from payment with NO_GRN.
  4. The same invoice number for the same vendor is rejected as a duplicate bill.
  5. An override by a non-finance role is refused and no payment flag is set.
Bottlenecks
  1. Matching in JavaScript by pulling three full tables into memory.
  2. The view recomputes GRN sums for all history; it needs filtering by PO before aggregation.
  3. Rounding differences between the invoice and the computed total flagged as variances.
  4. Duplicate invoice detection missing the vendor in the unique key.
  5. No index on invoices(vendor_id, invoice_no) turns duplicate checks into scans.

Screens to build: Invoice entry linked to a PO · Three-way match exception board · Line-level variance detail · Override dialog with reason

Data store: invoices(id, vendor_id FK, invoice_no, po_id FK, invoice_date, amount, UNIQUE(vendor_id,invoice_no)) · invoice_lines · view v_three_way_match · proc sp_match_invoice(invoice_id) · Mongo match_overrides

Minute-90 cut: keep the view and the exception list; drop the stored procedure and classify in the service layer.

PO-06

Budget check and fund blocking under concurrency

React + Vite + Ant Design · PostgreSQL · MongoDB for the ledger stream

The Physics department has ₹2,00,000 left in the equipment head. Three POs worth ₹80,000 each are submitted in the same minute. Exactly two should succeed.

Tasks
  1. Budget heads per department per financial year with allocated, committed and spent columns.
  2. On PO submission, block funds inside a transaction with a row lock on the budget head.
  3. Release the block on rejection or cancellation; convert it to spent on invoice payment.
  4. Budget utilisation screen with allocated, committed, spent and available.
  5. Append every movement to an immutable MongoDB ledger with a running balance.
Test cases
  1. Three concurrent ₹80,000 requests against ₹2,00,000 yield two successes and one 409 INSUFFICIENT_FUNDS.
  2. Rejecting an approved-but-unpaid PO restores available funds exactly.
  3. Payment moves the amount from committed to spent without changing the total.
  4. allocated = committed + spent + available holds after 200 random operations.
  5. A transaction that fails midway leaves no partial block.
Bottlenecks
  1. Check-then-update without a lock: the textbook lost update, and the most common failure in this problem.
  2. READ COMMITTED with a naive read means both requests see the same available balance.
  3. Locking the whole budget table instead of one row serialises the entire institution.
  4. Deadlock when two POs touch two budget heads in opposite order; lock in a fixed order by id.
  5. Deriving available by summing the ledger on every page load instead of keeping a materialised balance.

Screens to build: Budget utilisation dashboard per head · Fund-block confirmation on submit · Insufficient-funds error state · Ledger view with running balance

Data store: budget_heads(id, dept_id, fy, head, allocated, committed, spent, version) · fund_blocks(po_id FK UQ, head_id FK, amount, status) · Mongo budget_ledger append-only

Minute-90 cut: nothing. This problem is the concurrency control; drop the dashboard styling instead.

PO-07

Quotation comparison for a tender

React + Vite + Tailwind · MySQL · MongoDB for quotation documents

An RFQ goes to eight vendors. Six respond, each quoting differently on delivery time, warranty and freight. The committee needs a comparison sheet that names the lowest evaluated bid, not just the lowest price.

Tasks
  1. Create an RFQ with item specifications and a bid deadline; invite selected vendors.
  2. Quotation entry per vendor with unit rate, freight, warranty months and delivery days.
  3. Weighted scoring: price 60, delivery 20, warranty 20, computed server-side and explained in the UI.
  4. Side-by-side comparison table with the recommended vendor highlighted and a justification note.
  5. Convert the winning quotation into a draft PO in one click.
Test cases
  1. A quotation submitted after the deadline is refused with 422 BID_CLOSED.
  2. The lowest price with the worst delivery does not win when weights favour delivery.
  3. Quotations stay hidden from all users until the deadline passes.
  4. A vendor not invited to the RFQ cannot submit against it.
  5. Converting the winner creates a PO whose lines match the quotation exactly.
Bottlenecks
  1. Scoring done in React means every judge sees a different number after a refresh.
  2. Sealed-bid confidentiality broken by an endpoint that returns all quotations regardless of deadline.
  3. Deadline compared in local browser time instead of a single server timezone.
  4. Comparison query joining quotations to vendors to items with no covering index.
  5. Weights hardcoded, so a new tender policy needs a code change.

Screens to build: RFQ creation with vendor invite · Vendor quotation entry · Sealed state before the deadline · Comparison sheet with scores · Convert-to-PO confirm

Data store: rfq(id, rfq_no UQ, closes_at, status) · rfq_vendors(rfq_id, vendor_id, PK composite) · quotations(rfq_id, vendor_id, rate, freight, warranty_months, delivery_days, score, UNIQUE(rfq_id,vendor_id)) · Mongo quotation_docs

Minute-90 cut: fixed weights, no admin screen for them. Keep the deadline enforcement.

PO-08

PO amendment with version history

React + Vite + MUI · PostgreSQL · MongoDB for diffs

Six weeks after approval the quantity changes and the delivery date slips. Auditors must be able to see exactly what the PO looked like on any given date and who changed it.

Tasks
  1. Amendment creates a new version rather than editing in place; the original stays immutable.
  2. Version list with effective date, amended by, reason and amendment number.
  3. Field-level diff view between any two versions.
  4. Re-trigger approval when the amended value crosses a higher threshold.
  5. GRNs and invoices always resolve against the version effective on their document date.
Test cases
  1. Amending an approved PO produces version 2; version 1 rows are unchanged.
  2. An amendment that raises the value from ₹45,000 to ₹60,000 re-enters the approval chain.
  3. A GRN dated before the amendment validates against version 1 quantities.
  4. Amending a CLOSED PO is refused.
  5. The diff view shows exactly the two changed fields and nothing else.
Bottlenecks
  1. Copying every line on each version inflates storage; the alternative is a change-set model with its own complexity.
  2. Fetching "current version" without a partial index on is_current scans all versions.
  3. Foreign keys pointing at the PO id rather than the version id break temporal resolution.
  4. Two amendments created concurrently both claim version 2.
  5. Diffing large JSON blobs in the browser on every view.

Screens to build: Amendment form pre-filled from the current version · Version list · Side-by-side field diff · Re-approval notice banner

Data store: po_versions(po_id FK, version_no, effective_from, is_current, amended_by, reason, UNIQUE(po_id,version_no)) · versioned po_line_items keyed by version · Mongo po_diffs

Minute-90 cut: drop temporal resolution for GRNs; keep immutable versions and the diff.

EX-01

Exam timetable with clash detection

React + Vite + Ant Design · PostgreSQL · MongoDB for scheduling attempts

Third-year students take two electives from different departments. Scheduling both papers in the same slot means a re-exam for 180 students and a letter to the university.

Tasks
  1. Define exam sessions (date, forenoon/afternoon) and assign papers to slots via drag or select.
  2. Detect student clashes: any two papers in one slot sharing at least one registered student.
  3. Detect room and invigilator clashes across the same slot.
  4. Enforce a minimum gap rule between two papers of the same class.
  5. Publish the timetable, freezing it and notifying affected students.
Test cases
  1. Two electives sharing one student in the same slot raise a clash listing that student.
  2. Assigning the same hall to two papers in one slot is blocked.
  3. Papers scheduled on consecutive days pass a one-day-gap rule; same-day pairs fail.
  4. Publishing twice does not send duplicate notifications.
  5. Editing a published timetable requires a reason and bumps the version.
Bottlenecks
  1. Clash detection as nested loops over students × papers; a set-intersection query in SQL is orders faster.
  2. Running the full clash scan on every drag instead of only for the affected slot.

Fifteen-minute hardening pass

Security sweep

  • Every route has an auth check and an explicit role check.
  • Every id in a URL is checked for ownership, not just for existence.
  • All queries are parameterised; no string concatenation anywhere.
  • Mongo queries reject object-valued inputs that could carry operators.
  • .env and service-account files are in .gitignore.
  • Helmet, CORS allowlist and a rate limit on auth endpoints.
  • Error responses carry a code, never a stack trace.

Performance sweep

  • Run EXPLAIN on your two slowest queries and add the index it asks for.
  • Find the N+1: one query in a loop is the commonest one.
  • Every list endpoint has a limit, and the default is not 10,000.
  • Nothing heavy runs on the request thread: PDFs, email, image work.
  • React: memoise the table row, debounce the search box.

Railway: databases and API

  1. Create the project and add the databases first New Project, then Add Service twice: one MySQL or PostgreSQL (whichever your problem assigns) and one MongoDB. Railway injects DATABASE_URL and MONGO_URL into the project's shared variables. Never paste the credentials anywhere else.
  2. Deploy the API from GitHub Add Service, Deploy from GitHub repo, pick your repo. If the API lives in a subfolder, set Root Directory to server. Build command npm ci, start command npm run start. The server must listen on process.env.PORT and bind 0.0.0.0, or the deploy will build and then fail health checks.
  3. Set the API variables Reference the database variables rather than copying them: ${{MySQL.MYSQL_URL}} or ${{Postgres.DATABASE_URL}} and ${{MongoDB.MONGO_URL}}. Add the Firebase service account as a single-line JSON variable, plus ALLOWED_ORIGIN and ALLOWED_EMAIL_DOMAIN.
  4. Run migrations and seed From your machine: railway link, then railway run npm run migrate and railway run npm run seed. Running against the live connection string from your laptop is fine and is far faster than debugging a release command at minute 100.
  5. Generate the public domain Settings, Networking, Generate Domain. Confirm GET /health returns {"status":"ok","db":"up","mongo":"up"} in a browser before you touch the frontend.
  6. Turn on deploy on push Every merge to main redeploys. Keep a dev environment if you have the time; skip it if you do not.

Vercel: the React app

  1. Import the repo New Project, import from GitHub. Framework preset Vite. If the client is in a subfolder, set Root Directory to client. Build command npm run build, output directory dist.
  2. Add the environment variables Only VITE_-prefixed variables reach the browser, and everything with that prefix is public. The Firebase web config belongs here; the service account never does. Set VITE_API_URL to the Railway domain with no trailing slash.
  3. Handle client-side routing Without a rewrite, refreshing on /orders/142 returns a 404 from Vercel's static host. Add vercel.json with a catch-all rewrite to /index.html.
  4. Deploy and copy the URL The production URL is <project>.vercel.app. Every branch and pull request also gets its own preview URL, which is the fastest way to show a judge the before and after.
  5. Close the loop on CORS and Firebase Put the Vercel domain into ALLOWED_ORIGIN on Railway, and add it to Firebase Console, Authentication, Settings, Authorized domains. Missing either one produces a sign-in that works locally and fails in production.

How to submit

Eight steps, in this order. If you do these, you are submitted. There is nothing else to send, no form to fill and no email to write — the repository is the submission.

  1. Create the repository at minute 0 Name it campus-erp-<your-problem-id>, for example campus-erp-po-06. Make it public. Add .gitignore with .env, node_modules and any service-account JSON on the very first commit. A secret committed once stays in history even after you delete it, and it costs ten points.
  2. Build the folders exactly like this /client, /server, /db, /docs. Judges look in these four places and nowhere else. Anything outside them will not be found.
  3. Deploy once at minute 40, with almost nothing working Push a client that renders one page and a server with only /health. Connect Railway to /server and both databases; connect Vercel to /client. Confirm the live site can call the live API and that Gmail sign-in completes on the Vercel URL. Everything after this is automatic on push. Teams that leave this to the end do not finish.
  4. Build your five tasks on branches One branch per task, named feat/task-1-vendor-crud. Open a pull request, let the CI run, merge to main. Each merge redeploys both halves. If a task is not merged to main, it does not exist.
  5. Run your five test cases at minute 90 Not by clicking through the UI — run the suite. Fix what fails. If a test cannot pass in the time left, leave it failing and say so in the README. An honest failing test scores better than a deleted one.
  6. Take the fourteen screenshots at minute 100 The list and the filenames are in the section above. Put them in /docs/screenshots. Take them while the app still has seeded data in it.
  7. Write the README from the template below Ten minutes. This is the first thing a judge opens and often the only thing they read before they open your live URL.
  8. Tag the submission at minute 118 git tag v1.0-submission && git push --tags. Judges review that tag. Anything pushed after it is not looked at, so tag before you keep tinkering.
